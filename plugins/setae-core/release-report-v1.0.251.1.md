# SETAE v1.0.251.1 — 個体編集の公開設定

実装・検証日: 2026-08-28。v1.0.251を基準にした追加修正です。本番には未反映です。

## 使い方と変更内容

**個体情報を編集 →「公開・管理」→ 公開範囲と引き継ぎ受付を選択 →「保存」**で設定できます。QRの印刷画面を経由する必要はありません。

- 「公開・管理」を、公開Passportの公開範囲／管理の引き継ぎ／繁殖募集／コレクション管理に整理しました。保存済みの公開範囲も見出しに表示します。
- 公開範囲は「非公開」「基本情報を公開」「生活史を公開」の3種類です。各選択肢に公開内容を説明し、飼育者名・非公開メモなどを公開しないことを明記しました。
- **引き継ぎ受付中は「非公開」でも、受け渡し確認のため基本情報が公開されます。**これは既存の動作です。設定画面から分かるように説明を追加しました。受付終了時には未承認の申請を取り消します。
- 繁殖募集の設定はPassportの公開範囲から独立しています。アーカイブしても記録と公開範囲は維持し、引き継ぎ受付を終了します。
- QR側にも同じ設定部品を使用しました。引き継ぎ受付チェックの値 `1` を `on` と比較していた不具合を修正し、編集画面とQR側の表示を同期します。
- 変更していない公開項目は保存リクエストに含めません。通常の名前・メモ編集で、古い公開設定を再適用することを防ぎます。
- 公開設定を変更した保存が通信エラーになった場合、入力内容と選択した写真を画面に保持します。公開変更をオフラインキューへ自動登録しません。通常編集の既存オフライン動作は維持します。
- 古い下書きに公開項目がない場合、取得済みの設定を維持します。明示的にOFFにした下書きはOFFを復元します。写真ファイルを永続下書きとして保存する機能は追加していません。
- 公開設定を取得できない場合は「未確認」と表示し、推測で非公開へ変更しません。譲渡済み記録では公開範囲・引き継ぎ受付を変更できません。新規登録は従来どおり非公開で作成します。
- 既存の入力部品・余白・色・操作サイズを使用し、デスクトップ、幅390px、幅320px、ダーク表示を確認しました。

## API・後方互換性

- 個体更新API `/spiders/{id}` のJSON・写真付きmultipartの両方で、任意項目 `qr_visibility` と `transfer_enabled` を受け付けます。
- `qr_visibility` は `private` / `basic` / `life_history`、`transfer_enabled` はbooleanまたは0/1を検証します。省略した項目は変更しません。
- 公開変更がある場合、所有者・譲渡済み状態・アーカイブ状態・入力値を通常編集前に検証します。無権限や不正値で通常項目まで更新することを防ぎます。
- 既存のQR設定APIと旧 `public` booleanの互換動作を維持します。公開ページの情報許可リストは拡張していません。
- v1.0.251の課金・登録枠・プレミアム権限の仕様は変更しません。既存の契約・データを変換する処理や、将来の事業機能は追加していません。
- 同梱vendorと前回リリース報告書は前回配布ZIPと同一であることを梱包時に検査します。

## DB変更

**テーブル・カラムの追加、スキーマ変更、データ移行、既存データの一括更新はありません。**

設定を保存した対象個体の既存メタ `_setae_qr_public_mode`、`_setae_qr_public`、`_setae_transfer_enabled`、既存QRターゲットを更新します。受付終了時には対象の未承認引き継ぎ申請を取り消します。未変更項目は維持します。

公開設定・QRターゲット・既存未承認申請の取消は、既存Entitlementsのトランザクション基盤を使います。必要なInnoDB、autocommit、所有者ロックを確保できない場合はエラーで停止します。

## 既知の制約・未実施

1. **実WordPress/MySQLでの導入・更新・同時接続テストは未実施です。**実際のInnoDB、所有者ロック、外部オブジェクトキャッシュ、既存サイト設定との組み合わせは確認していません。実SMTP・Stripe、物理スマートフォンも未検証です。
2. **個体情報の保存全体が原子的になったわけではありません。**通常項目・写真・飼育場所などの既存保存が完了した後で、公開設定の保存が失敗する可能性があります。今回のトランザクション範囲は公開設定・QRターゲット・既存未承認申請の取消です。通信エラー時には保存結果を断定せず、再取得して状態を確認する必要があります。
3. 申請作成側は申請者のロックを使用する既存構造のため、受付終了と新規申請が同時に走ると、取消処理の直後に未承認申請が残る競合余地があります。**受付OFF中はその申請を承認できず、所有権は移りません。**この拒否動作はテスト済みですが、実DBの同時実行を完全に直列化したものではありません。
4. 公開変更がない通常編集のオフライン同期は従来どおりです。公開変更を伴う保存は自動再送しません。通信が不確かな場合は、接続回復後に取得済み設定を確認してください。
5. 今回は関連ブラウザ検証を選択して実行しています。前回の全ブラウザスイート・性能ベンチマークをすべて再実行したものではありません。v1.0.251で記録された大量データ性能検証の失敗は未解決・未再計測であり、成功扱いしていません。詳細は保持した `release-report-v1.0.251.md` を参照してください。
6. 検索エンジンには登録禁止を指定しますが、リンクを知る人からの共有や保存を防ぐものではありません。受付中の基本情報公開には上記の例外があります。
