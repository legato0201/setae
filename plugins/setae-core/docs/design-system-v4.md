# SETAE UI System v4

## Product direction

SETAE is a Living Collection Workbench. Application controls remain neutral and modern; natural-history language is reserved for taxonomy, specimen identity, records, photography, provenance, and physical labels.

## Visual art direction

Version 1.0.241 defines the product craft target as **Natural History Museum x Modern Research Database**. The interface should feel precise, quiet, archival, and operational. Information hierarchy comes from typography, rules, whitespace, alignment, and density rather than decorative cards or novelty motion.

- System UI type is the default. No unshipped web font may appear in the UI stack.
- Taxonomic names alone use the serif taxon face and italic treatment.
- Identifiers, dates, counts, measurements, temperatures, and humidity use mono with tabular numerals.
- English eyebrows identify a page or major record context. They are not repeated above every ordinary subsection.
- Accent green identifies selection and the principal action. It is not a general decoration color.
- Shadows belong to popovers, overlays, toasts, and update notices. Ordinary sections and rows are separated with rules and whitespace.
- Motion belongs to disclosure, overlays, progress, loading, and short feedback. Cards do not float and photographs do not zoom on hover.
- Physical labels preserve white paper, black ink, fixed dimensions, and print typography independently from the application theme.

The visual audit that motivated this pass is recorded in `docs/visual-audit-v1.0.241.md`. Each material correction maps back to a `VC-*` finding in that document.

## Craft tokens

Four semantic weights are permitted: `--weight-regular`, `--weight-medium`, `--weight-semibold`, and `--weight-bold`. Typography uses `--leading-display`, `--leading-ui`, or `--leading-body`; eyebrows and identifiers use the dedicated tracking tokens.

Rows use `--row-inset` or `--row-inset-compact`. Page geometry uses 16px, 24px, and 32px responsive gutter roles. Icon wrappers use the small, medium, large, or navigation icon tokens without rewriting custom SVG fill or stroke.

Selection uses `--bg-selected` and `--border-selected`. Keyboard focus remains a separate `--focus-ring` state, and multi-selection remains a checkbox state. Elevation uses only the popover, overlay, or toast shadow role.

Entering overlays and feedback may travel 4-8px using `--motion-enter` and `--ease-emphasized`. Reduced-motion mode disables transform animation, shimmer, and smooth scrolling.

## Reference implementation

Version 1.0.220 rebuilds Collection as the reference screen. It owns the complete flow from app navigation through workspace header, toolbar, registry, inspector, gallery, and batch-status dialog. Existing query, selection, bulk-record, QR, and specimen-opening behavior is retained.

Desktop uses a 216px navigation rail, a fluid workspace, and a 300px inspector. Registry is the default Collection view. Gallery remains an optional photographic view. Mobile uses an equal-height five-item navigation and opens specimen detail directly.

## Rendering contract

Collection controls must be generated by `assets/app/components/primitives.js`. Feature and page files may compose controls but must not emit raw `button`, `input`, `select`, or `textarea` elements.

Shared structure is split by responsibility:

- `styles/reset.css`
- `styles/app-frame.css`
- `styles/components/workbench.css`
- `styles/patterns/workspace.css`
- `styles/patterns/registry.css`
- `styles/screens/collection.css`

Version 1.0.240 retires the compatibility layout. Every selector now belongs to Foundation, a Component, a Pattern, App Frame, a Screen, or Utilities. A new catch-all compatibility stylesheet must not be introduced.

## Transactional workflow reference

Version 1.0.234 promotes Quick Record to the transactional workflow reference implementation. It owns the canonical pattern for:

- action selection and priority
- contextual specimen identity
- transactional form composition
- mobile sheet composition
- independently scrolling form bodies
- persistent action footers
- busy locking and duplicate-submit prevention
- form error recovery without input loss

Quick Record feature files compose controls from `assets/app/components/primitives.js`. They must not emit raw `button`, `input`, `select`, or `textarea` elements. `actionRow()` is the standard list action and `quantityStepper()` owns the decrement, numeric input, and increment structure.

Quick Record screen rules live only in `styles/screens/quick-record.css`.

## Operational workbench reference

Version 1.0.235 promotes Today to the operational workbench reference implementation. It owns the canonical hierarchy for:

- date-led operational context
- overdue, remaining, and handled work metrics
- priority-first compact task queues
- secondary handled and upcoming information
- normal journal presentation without widget surfaces
- editing-only dashboard surfaces and controls

Today renders the task workspace before journal sections. When overdue and due-today work exceeds eight items, the initial queue allocates the eight visible rows to overdue work first and then to today's work. Full counts remain visible and the user can expand or collapse the queue without changing the Care Task data contract.

Today page and Dashboard Editor controls must be composed from `assets/app/components/primitives.js`. Today-specific geometry lives in `styles/screens/today.css`; the shared task grammar lives in `styles/patterns/task-workspace.css` for both Today and standalone Care.

`dateField()` owns date, month, time, and local date-time controls for every transactional screen. Desktop keeps the visible native control. In iOS touch environments, the native input remains the transparent interaction and FormData layer while `date-field-frame` renders the controlled value and calendar icon. Feature screens must not hide the native input, remove native appearance, call a custom picker, or replace this shared contract with local width rules.

## Chronological ledger reference

Version 1.0.236 promotes Records to the chronological ledger reference implementation. It owns the canonical pattern for:

- date-led history without per-record cards
- event type, target identity, and summary hierarchy
- consistent specimen, enclosure, and nursery targets
- trailing action menus with danger actions separated at the bottom
- compact mobile stacking without a fixed date column
- primitive-based filters, empty states, and record actions

The reusable row structure lives in `styles/patterns/ledger.css`; Records-specific presentation lives in `styles/screens/records.css`. Records must not emit raw `button`, `input`, `select`, or `textarea` controls.

## Group registry and development reference

Version 1.0.237 promotes Nursery to the Group Registry / Development Workspace reference implementation. Nursery composes four existing UI System contracts instead of introducing a separate visual language:

- Workspace for group identity, action hierarchy, and care status
- Registry for active groups and the responsive specimen register
- Ledger for nursery-level and baby-level chronological history
- Transactional Form for group creation, care events, bulk updates, promotion, and QR selection

Active groups are divider-separated Action Rows rather than large cards. The detail page uses the Collection header as its only page header, keeps routine group records in the primary toolbar, and places baby-level bulk changes in a secondary menu. Desktop uses the common Registry Table; mobile uses the common Mobile Registry List without horizontal scrolling.

Nursery feature and Care Plan controls are composed from `assets/app/components/primitives.js`. Nursery-specific screen rules live only in `styles/screens/nursery.css`.

## Husbandry workbench reference

Version 1.0.238 promotes Husbandry to the Enclosure Registry / Environmental Operations reference implementation:

- Feeder inventory belongs to Husbandry and uses an operational summary, divider-separated registry rows, and the shared chronological ledger.
- Enclosure detail has one workspace header and presents environment, housing properties, occupancy, care plan, records, and occupancy history in operational order.
- Enclosure, specimen, and nursery care plans share `styles/patterns/care-plan.css` while retaining independent models and storage contracts.
- Husbandry views and enclosure forms compose controls through UI primitives; screen-specific layout lives only in `styles/screens/husbandry.css`.

## Runtime rendering contract

Version 1.0.243 separates the authenticated application into persistent render islands. `assets/app/runtime/render-coordinator.js` owns the only full App root mount. Normal application actions update the Page, Rail, Mobile Bar, Mobile Navigation, Sync, Error, Overlay, Feedback, or Update root independently. Toast, sync status, update notice, global error, Modal, and Sheet changes must preserve the Page root, active form, selection, scroll position, and active camera element.

Full mounts are limited to Boot, Connection Error, Authentication, Public Mode, the transition into the authenticated App, Logout, and Mock Mode changes. Feature code must not introduce another App root replacement path or a private diff engine.

Records and Nursery use the shared `components/progressive-list.js` contract: 100 initial rows, 100 additional rows, a persistent explicit load-more action, an `aria-live` announcement, focus continuity, and route restoration. Nursery owns one semantic responsive table; bulk actions continue to operate on the explicitly selected codes or whole group rather than the visible window.

Collection search uses `queries/animal-search-index.js`. The normalized index is rebuilt only when the animal data array changes, while IME-safe search continues to update the Collection results region without replacing the App Frame or Inspector.

Media uses native `loading`, `decoding`, `fetchpriority`, and width/height hints. Only the currently inspected primary image may be eager/high priority. A lazy image starts its timeout only after entering the viewport or the 600px observer margin. Print preparation promotes lazy images to eager, and offscreen content uses owner-scoped `content-visibility` with print and interactive-state exclusions.

`tests/ui-system-v4-collection-unit.js` enforces Primitive-only controls in Collection, tokenized colors, typography and spacing, the three responsive viewport bands, Registry default mode, and App Frame dimensions. `tests/ui-system-v4-quick-record-unit.js` applies the same architecture gate to transactional workflows. `tests/ui-system-v4-today-unit.js` verifies the operational hierarchy, compact queue allocation, Primitive-only Today controls, and Today screen isolation. `tests/ios-date-field-unit.js` protects the controlled iOS date interaction contract, `tests/ui-system-v4-records-unit.js` protects the Ledger pattern and existing record actions, `tests/ui-system-v4-nursery-unit.js` protects the Group Registry, responsive Specimen Register, transactional forms, and Nursery screen isolation, and `tests/ui-system-v4-husbandry-unit.js` protects the Enclosure Registry, shared Ledger and Care Plan patterns, Primitive-only controls, and Husbandry screen isolation.

## CSS ownership

The runtime layer order is `reset`, `foundation`, `components`, `app-frame`, `patterns`, `screens`, then `utilities`.

- Component ownership: reusable controls and self-contained UI internals. `components/media.css` owns media frames, placeholders, attribution, and media fallback. `components/specimen-card.css` owns reusable specimen-card internals. `components/update-notice.css` owns the application update notice.
- Pattern ownership: reusable multi-component grammar. `patterns/task-workspace.css` owns task groups, rows, progress, due state, and handled history.
- Screen ownership: page-specific geometry and local extensions only. `screens/auth.css` owns authentication, boot, and connection states. `screens/collection-editor.css` owns Saved View and Card Editor presentation.
- App Frame ownership: navigation rail, mobile app bar, bottom navigation, content viewport, and application-level responsive geometry only.
- Foundation ownership: document root, page rhythm, typography roles, and shared content widths.

A screen may extend a component with a scoped selector such as `.collection-gallery-v4 .animal-card`, but it must not redefine the complete component contract. New selectors must be placed with a named owner; adding a compatibility catch-all is prohibited.

The 1500px breakpoint is reserved for Collection photo-density only. It adds a fourth gallery column when the full 1360px collection workspace has sufficient room; all other responsive behavior uses the 767px, 768–1199px, and 1200px bands.

## Control density and label visibility

Compact density never hides semantic content. Density modifiers such as `compact`, `is-compact`, `is-dense`, and `is-small` may reduce control height, spacing, type size, padding, or mark size, but they must not change whether a label, description, or accessible name exists.

Icon-only controls require an explicit screen-reader-only label contract. For `checkboxControl()`, use `labelMode: 'sr-only'` only where surrounding context makes the visual label redundant, such as Collection selection and select-all controls. Visible preference controls always retain visible labels, including Settings, Label Studio, forms, notifications, care rules, QR options, and user preferences. The default is `labelMode: 'visible'`.

Compact density never hides semantic content. Icon-only controls require explicit sr-only labels. Visible preference controls always retain visible labels.

コンパクト密度は意味のある情報を非表示にしない。`compact`、`is-compact`、`is-dense`、`is-small`は高さ、間隔、文字サイズ、余白、マークサイズだけを調整し、ラベル、説明、アクセシブルネームの有無を変更しない。

Icon-onlyコントロールでは、Screen Reader専用ラベルを明示的に指定する。`checkboxControl()`の`labelMode: 'sr-only'`は、コレクション選択や全選択のように周辺文脈だけで視覚的意味が成立する場合に限る。設定、ラベルスタジオ、フォーム、通知、飼育ルール、QRオプション、ユーザー設定では、常に見えるラベルを維持する。既定値は`labelMode: 'visible'`とする。
